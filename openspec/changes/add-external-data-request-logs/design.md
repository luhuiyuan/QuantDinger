## Context

QuantDinger 的外部市场、宏观、资讯和目录数据调用分散在 `app/data_sources/` 与 `app/data_providers/` 中；直接 `requests` 调用和 yfinance、AkShare 等第三方库并存，当前没有统一的出站 HTTP 拦截点。系统已有 PostgreSQL、管理员 JWT 鉴权、Celery Beat `maintenance` 队列、结构化请求 ID 上下文和设置页，可作为本变更的基础设施。

该能力面向管理员排障与提供方健康观察，而不是用户访问审计、交易审计或网络包追踪。部署主机资源有限，日志存储、查询和清理必须使用索引、分页和受控批处理。

## Goals / Non-Goals

**Goals:**
- 对每个真实外部提供方逻辑调用记录一个脱敏、可查询的 `Provider Attempt`。
- 在降级链路中保留提供方顺序和每次尝试的结果，并以固定结果枚举支持可靠统计。
- 提供管理员专属概览、分页明细、详情和保留策略配置。
- 每日自动清理成功与异常记录，且日志写入或清理失败不影响数据请求和业务任务。

**Non-Goals:**
- 不记录入站 HTTP、交易所/经纪商请求、订单执行或 Agent 审计。
- 不拦截或逐包记录 yfinance、AkShare 等第三方库的内部网络调用。
- 不保存 API Key、认证头、Cookie、完整 URL 查询串、完整响应体或完整堆栈。
- 不在日志页面提供重试、重放、删除单条记录或一键清空。

## Decisions

### 逻辑级适配器边界而非全局 HTTP monkey patch

新增轻量 `ExternalDataRequestLogService` 及显式 `ProviderAttempt` 上下文/辅助器，供拥有“提供方、数据域、操作、标的范围、降级序号”语义的适配器调用。辅助器在尝试结束时以 `finally` 记录耗时和固定结果分类；调用方明确映射超时、限流、网络、提供方业务错误、无效响应和跳过。

选择此方案是因为全局拦截 `requests` 无法覆盖第三方库，也无法可靠获得业务操作和降级语义。替代方案是 monkey patch 全局 HTTP 客户端；它会记录无关调用、遗漏库内请求并增加测试/运行时风险，故不采用。

第一期按提供方适配器分批接入，并要求每个接入的逻辑尝试都覆盖成功、异常和受控跳过路径。缓存命中只由缓存层累加轻量计数器，不创建 `Provider Attempt` 行。

### PostgreSQL 持久化、固定枚举与脱敏摘要

新增请求日志表，至少包含：递增 ID、发生时间、提供方、数据域、操作名、调用来源、标的摘要/数量、降级序号、重试次数、耗时、结果枚举、HTTP 状态、截断错误摘要和关联 `request_id`。为默认倒序查询、结果/提供方过滤和保留清理建立复合索引。日志行不关联或暴露用户密钥；参数摘要由统一脱敏/截断函数生成。

成功与异常放在同一张表，避免概览、时间线和降级链路跨表拼接。结果使用固定枚举而非自由文本，以保证保留期、筛选和统计稳定。替代方案是普通应用日志或成功/错误分表；前者不可按管理员查询，后者会拆散同一次调用链路，均不采用。

### Fail-open 写入与受控存储失败观察

日志写入在数据提供方调用完成后执行；写入异常被捕获、发出结构化应用错误/指标并返回原始数据请求结果。日志服务不得递归记录自己的失败。管理员概览显示最近日志写入健康状态和最近清理结果。

这避免 observability 数据库故障变成行情或同步不可用的单点故障。代价是日志可能出现缺口；通过健康状态和应用日志使缺口可见。

### 管理 API、页面和设置集成

新增 Human API 的私有管理员端点：概览、分页列表、详情和日志设置/清理状态。所有端点使用 `@login_required` 与 `@admin_required`，遵循 `{code, msg, data}` 信封和既有分页形状。新端点标记 `x-visibility: private` 并更新 `docs/api/openapi.yaml`。

Vue 新增管理员路由“数据请求日志”，展示近 24 小时概览、筛选明细与详情抽屉；保留期/开关在现有 `/settings` 的管理员配置中编辑。前端连接不支持新端点的旧后端时显示能力未启用，不伪造数据。

### 每日批量保留清理

在 `app.tasks.maintenance` 增加 maintenance 队列任务，并在 Celery Beat 每日调度。配置默认成功/跳过记录 30 天、异常记录 90 天及清理开关；设置值必须有保守下限。删除按 ID/时间有界批次执行、每批提交，记录开始/完成时间、删除数量和失败摘要到清理状态表或现有设置状态存储。

选择每日批量删除而非请求内同步删除，以避免读取路径上的长事务和锁竞争。清理任务须可重入；多次运行只删除仍满足保留条件的记录。

## Risks / Trade-offs

- [适配器分散，第一期可能遗漏提供方] → 以共享辅助器和接入清单覆盖主要适配器；测试验证已接入路径，后续提供方按同一契约接入。
- [高频成功记录增长过快] → 不记录缓存命中、使用分页和索引、成功记录较短保留期、每日批量清理。
- [错误摘要意外包含敏感值] → 统一白名单字段和敏感键/URL 查询串清洗；测试 API Key、Authorization、Cookie 不会持久化或返回。
- [清理与管理员查询竞争] → 时间索引、短批次事务和只读分页查询；清理失败 fail-open 并保留运行状态。
- [旧后端滚动升级期间前端请求失败] → 前端将明确显示能力未启用，不影响其他设置/管理页面。

## Migration Plan

1. 添加幂等 PostgreSQL 表、索引和默认配置；部署时不影响现有数据或请求路径。
2. 部署后端日志服务、适配器接入、管理员 API 与每日维护任务；日志写入失败仍不阻断请求。
3. 部署 Vue 管理页面与设置项；用管理员账户验证概览、筛选、权限和旧后端降级。
4. 观察一轮清理任务与表增长后再调整配置，不做全表删除。

回滚时先移除前端入口和新 API 调用，再停用日志开关/任务。保留已写日志表以避免破坏性回滚；后续经人工确认后才删除新表。
